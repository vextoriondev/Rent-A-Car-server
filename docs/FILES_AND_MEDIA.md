# Files & media: storage, database schema, API, deployment

One central system serves every module (drivers, owners, clients, vehicles, agreements, maintenance, transactions).
Code: `rentals/models/attachments.py`, `rentals/services/files/` (`storage.py`, `images.py`, `attachments.py`), `rentals/api/attachments.py`.
Frontend: `lib/files.ts`, `components/features/files/` (`attachment-panel.tsx`, `profile-photo.tsx`, `storage-usage.tsx`).

## 1. Storage architecture

* File **bytes** live in object storage. The database holds only metadata and the storage key (never image/document binary).
* Two backends behind one interface (`FILE_STORAGE_BACKEND`):
  * `s3`: any S3-compatible service (Cloudflare R2 recommended). Persistent, works with Vercel + Railway, downloads are 5-minute signed links so file bytes do not pass through Django.
  * `filesystem`: `PRIVATE_MEDIA_ROOT/attachments`. For development, or one server with a mounted volume (Railway volume at `/data`). **Never use it on Vercel** (ephemeral disk).
* Keys are generated by the server: `org-{orgId}/{entity}/{uuid}/{variant}.{ext}`. A client-supplied name is stored only as display text. Every key is validated again in the storage layer (no `..`, no leading `/`).
* Private by default: nothing is public; every request is authenticated and permission-checked. Same bytes in two organizations are stored twice on purpose (no cross-organization dedupe).

### Provider evaluation (approximate list prices; confirm on each provider's pricing page before committing)

| | Cloudflare R2 | AWS S3 (Standard) | Backblaze B2 |
|---|---|---|---|
| Storage | about $0.015 / GB-month (10 GB free) | about $0.023 / GB-month | about $0.006 / GB-month |
| Download bandwidth | **no egress fee** | about $0.09 / GB after the free tier | free up to ~3x stored, then low |
| Requests | cheap, small free tier | cheap | cheap |
| S3 API / boto3 | yes | native | yes |
| Fit here | **chosen**: photos and scans are downloaded often, egress is the cost that surprises; free tier covers a small fleet | fine, costs more | cheapest storage, smaller ecosystem |

Decision: **Cloudflare R2** (S3-compatible, so switching provider is a configuration change, not a code change). No new paid service is added beyond the bucket.

## 2. Required environment variables (backend)

| Variable | Meaning |
|---|---|
| `FILE_STORAGE_BACKEND` | `s3` or `filesystem` (default: `s3` if `S3_BUCKET` is set, else `filesystem`) |
| `S3_BUCKET` | bucket name |
| `S3_ENDPOINT_URL` | R2: `https://<account-id>.r2.cloudflarestorage.com` (empty for AWS S3) |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | an API token limited to this bucket (Object Read & Write). **Backend only; never in the frontend or the repo** |
| `S3_REGION` | `auto` for R2, the region for AWS |
| `S3_KEY_PREFIX` | optional folder inside the bucket (default `tasin`) |
| `FILE_SIGNED_URL_TTL` | seconds a signed download link lives (default 300) |
| `ATTACH_MAX_IMAGE_MB` / `ATTACH_MAX_PDF_MB` / `ATTACH_MAX_DOC_MB` | per-file limits (15 / 10 / 10) |
| `ATTACH_MAX_FILES` / `ATTACH_MAX_TOTAL_MB` | per request (10 files / 40 MB) |
| `ATTACH_MAX_PIXELS` | decompression-bomb guard (60 million pixels) |
| `ATTACH_PHOTO_QUALITY` / `ATTACH_DOC_QUALITY` | WebP quality for photos (78) and for scans of documents (90) |
| `ATTACH_DOC_LARGE_SIZE` | longest side of a scan's preview variant (2200 px) |

### Cloudflare R2 setup (production)
1. Cloudflare dashboard > R2 > Create bucket (private, no public access, no custom domain).
2. R2 > Manage API tokens > Create token with *Object Read & Write* on that bucket only. Copy the Access Key ID, Secret and the account endpoint URL.
3. In Railway > backend service > Variables set the variables above (`FILE_STORAGE_BACKEND=s3`, `S3_*`). Redeploy. Do not copy the secret anywhere else.
4. No CORS configuration is needed: the browser never talks to the bucket for uploads (they go through the API), and downloads are plain redirects to a signed link.
5. Check: open Settings > Files & storage (shows "cloud object storage"), upload a photo, redeploy the backend, and confirm the photo is still there.

## 3. Database schema (`rentals_attachment`)

`id` UUID pk · `organization` FK · exactly one of `party` / `vehicle` / `agreement` (TasinAgreement) / `maintenance` / `transaction` FK, all `ON DELETE CASCADE` (a `CHECK` constraint rejects a row with zero or two owners; deleting the record deletes its attachment rows, so there are no orphans) · `kind` (`profile` | `photo` | `document`) · `category` · `description` · `original_name` · `stored_name` · `mime_type` (sniffed from content) · `extension` · `storage_provider` · `storage_key` · `original_key` · `variants` JSON (`thumb`/`medium`/`large`: key, size, width, height) · `size_original` · `size_stored` · `width` · `height` · `sha256` · `status` (`uploading` | `processing` | `completed` | `failed`) · `error` · `upload_key` · `uploaded_by` · `created_at` · `updated_at`.

Constraints: one `profile` per party and per vehicle (conditional unique); `(organization, upload_key)` unique when set (retry safety). Migration `0041_attachments` (additive; existing tables untouched; the older `Document` / `PrivateDocument` tables and endpoints keep working).

## 4. Image optimization

* The file must decode as JPEG/PNG/WebP; pixel count is capped; EXIF orientation is applied; **all metadata including GPS is dropped**.
* Variants are WebP: thumb 240 px, medium 900 px, large 1600 px (longest side, **never upscaled**, transparency kept).
* **Photos** (`profile`, `photo`): only the variants are stored (no duplicate original).
* **Documents** that are images (scans, receipts, certificates): the original is kept and only re-encoded without metadata if it carried GPS; previews use quality 90 and a 2200 px large variant so text stays legible.
* The browser also shrinks phone photos over ~1.2 MB (max 2400 px) *before* upload to save bandwidth; scans are never touched in the browser.
* Processing runs inside the request (a 15 MB photo takes about a second or two). A file that decodes but cannot be processed is stored as `failed` with its original kept and can be retried (`POST /files/{id}/retry`). Celery is not required; `status` is in place for moving processing to a worker later.

## 5. API (all under `/api/v1/orgs/{org_id}/`)

| Method and path | Purpose |
|---|---|
| `GET/POST tasin-owners / tasin-drivers / tasin-clients / tasin-vehicles / tasin-agreements / tasin-maintenance / tasin-transactions /{id}/files` | list / upload (multipart: `files` (repeatable), `kind`, `category`, `description`; header `Idempotency-Key`) |
| `GET /files/{id}` · `PATCH /files/{id}` · `DELETE /files/{id}` | metadata / edit category and description / delete |
| `GET /files/{id}/content?variant=thumb\|medium\|large&download=1` | the bytes (signed redirect on S3, streamed on filesystem) |
| `POST /files/{id}/make-primary` · `POST /files/{id}/retry` | promote a photo to main picture / reprocess a failed one |
| `GET /files-limits` · `GET /files-usage` | limits and categories / storage overview (needs `settings` view) |

Upload response: `{items: [...], errors: [{fileName, code, message}]}` (partial success is allowed). Errors use the usual `{detail, code}` body (400 invalid, 403 forbidden, 404, 413 too large, 503 storage unavailable).

Categories: owner `nid, ownership, financial, other` · driver `nid, license, passport, other` · client `trade_license, nid, other` · vehicle `registration, insurance, fitness, tax_token, inspection, route_permit, front, rear, side, interior, damage, other` · agreement `agreement_pdf, scan, stamp_paper, signed, legal, other` · maintenance `bill, invoice, damage, other` · transaction `receipt, bill, voucher, other`.

## 6. Permission rules

* Every route needs a session (401), membership in the organization (403), and the module's RBAC action: view to list/see, create to upload, edit to change/make-primary/retry, delete to delete. The module is the file's record (owners, drivers, clients, vehicles, agreements, maintenance, accounts).
* **Identity papers** (categories `nid`, `passport`, `license`) are hidden from the list and refused on fetch for anyone without *edit* permission on the module.
* An entity or file id from another organization is a 404/403; ids are never trusted without the organization check.
* Uploads: type decided by content (magic bytes / zip structure / full image decode), not extension or the declared type; Word files with macros are rejected; sizes and counts checked on the server; storage names are server generated; files are never executed; responses carry `X-Content-Type-Options: nosniff`, a sandboxing `Content-Security-Policy`, and private caching only. A malware-scanner hook (`scan_hook`) is the extension point (none configured).
* Uploads, replacements, deletions, make-primary, downloads of originals and edits are written to the audit log (`attachment.*`).

## 7. Deployment (Vercel + Railway + R2)

* Vercel runs only the frontend; the browser calls `/backend/...`, which Next.js rewrites to Railway. File **uploads go through the same rewrite**. Vercel limits request bodies on its own functions (about 4.5 MB); whether a rewrite to an external origin has the same limit **must be tested on the real deployment** before relying on large PDFs. The browser pre-shrinks photos below that anyway. If large PDFs are rejected there, the fix is a direct-to-R2 presigned upload (not implemented).
* Environment: `DJANGO_CSRF_TRUSTED_ORIGINS` must contain the frontend origin (uploads are POSTs). No storage secret is ever exposed to the frontend.
* The migration runs in Railway's pre-deploy step (`0041`).
* Railway `startCommand` already uses gunicorn with a 60 s timeout, enough for image processing.

## 8. Backup and recovery

* Database: Neon point-in-time restore / branches. Files: enable R2 object versioning or periodic bucket replication; the database rows and the bucket must be restored to the same point in time.
* `python manage.py cleanup_orphan_files` lists objects without a row (default: report only; `--delete` removes those older than 24 h) and lists rows whose object is missing. Run it after restoring.

## 9. Troubleshooting

| Symptom | Cause / fix |
|---|---|
| 503 "File storage is not available" | wrong `S3_*` values or bucket name; check Railway logs; credentials need Object Read & Write |
| Upload 403 | the user lacks create/edit permission on that module, or the CSRF origin is not trusted |
| Upload 413 | over a limit (see `/files-limits`) or the hosting platform's body limit |
| Photo shows initials instead of a picture | no main picture yet, or the file is still `processing`/`failed` (retry) |
| After a restore some images are 404 | run `cleanup_orphan_files` to list rows with missing objects |
