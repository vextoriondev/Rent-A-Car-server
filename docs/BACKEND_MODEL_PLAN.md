### Gaps found by reading the code (each is owned by a milestone below)

1. **Identity** — no link from `Party` to a login user, no branch, no object-scoped access; `Membership` roles don't include owner/driver/customer/mechanic. (M1, M10)
2. **Terms are not effective-dated** — rent/salary/rules live on `Agreement`; `Expense.rule_snapshot` is a 3-key JSON copy. No `AgreementVersion`, no revision history. (M2, M3)
3. **Vehicle has one owner forever; agreement has one driver forever** — no `VehicleOwnership` / `DriverAssignment` history; only `create_agreement` checks vehicle overlap (`agreements/quick` does not). (M2)
4. **Expense engine is a stub** — only `fuel`/`repair` have rules; categories hard-coded in the service; `paid_by` limited to operator/owner; approval threshold `5000` hard-coded in `record_expense`; no `Approval` model, no proof-required, no override with permission+reason, no duplicate warning (unique only per period+reference), no draft state. (M3)
5. **Ledger is partly a string convention** — `JournalLine.account` is free text, lines carry no party/agreement/period dimension, and `statement()` is computed from obligations/allocations/expenses, **not** from the journal (two sources of truth, no reconciliation test). Only 3 obligation kinds: no variable charges, credits, adjustments, opening balances, carry-forward, invoices. `salary_advance` is allocated to the driver-salary obligation exactly like a payout, so statements can't show advances separately. (M4)
6. **Payments** — no reversal (`reverse_payment` doesn't exist), no unapplied credit, no payer/recipient/payment account (`method` is a free string), no direct owner→driver / customer→driver payments, no closed-period policy. (M5)
7. **Settlement is one timestamp** — `Period.closed_at`; no `Settlement`/`SettlementLine`, no readiness checks, approval, reopen, late-entry adjustment. `close_period` refuses negative balances instead of expressing "owner owes operator". (M6)
8. **Notifications never send** — `NotificationOutbox` rows are created, but **nothing enqueues `deliver_notice`** (no `.delay()`/`on_commit`); no templates, consent/preferences, delivery-attempt records, channel adapters, in-app inbox/read state; `/notifications/{id}/retry` only flips state back to `queued`. Only expense-posted-to-owner, payment, rent-issued and settlement-closed events exist. (M7)
9. **No documents, no audit trail, no maintenance** — receipts aren't stored (the frontend keeps only a file name); no `AuditEvent`, `Document`, `MaintenanceCase`. (M8)
10. **No reports/exports**; list endpoints are capped slices (`[:200]`), only `agreements` paginates. (M9)
11. **Snapshot serializes money as floats** (`float(a.customer_rent)` in `/snapshot`) while other endpoints use decimal strings; the frontend depends on the snapshot shape (see contract below). (M9, with a frontend change)
12. **Concurrency is untested on PostgreSQL** — tests run on SQLite, which ignores `select_for_update`; README already admits it. (M0)

## Frontend contract (do not break silently)

The Next.js app (API mode, `NEXT_PUBLIC_RENTFLOW_API_MODE=1`) calls, through a same-origin `/backend/*` rewrite with session cookie + `X-CSRFToken`: `GET /me`, `GET /csrf`, `GET /orgs/{org}/snapshot?month=2026-09-01`, `POST /orgs/{org}/agreements/quick`, `POST /orgs/{org}/agreements/{id}/periods?month=…`, `POST /orgs/{org}/expenses`, `POST /orgs/{org}/payments` (both with `Idempotency-Key`), `POST /orgs/{org}/expenses/{id}/approve|reverse`, `POST /orgs/{org}/periods/{id}/close`, `POST /orgs/{org}/notifications/{id}/retry`. `snapshot` returns `{agreements[], entries[], notices[], closed[], backend:{orgId, periodIds, obligationIds, expenseIds}}` with ids like `AGR-{pk}`, `EXP-{pk}`, `PAY-{payment}-{alloc}`, `NT-{pk}`. Snapshot numbers are `float`; `obligationIds` keys are `customer|owner|driver`. Payload fields: expense `{period_id, category, amount, event_date, paid_by, responsible, offset_owner, reference, description}`; payment `{kind, amount, reference, method, event_date, allocations:[{obligation_id, amount}]}`.

The frontend's API mode was **not re-verified after the Phase 1 refactor** — do a manual pass (below) before M2.

## Cross-cutting rules (apply to every milestone)

- **Money:** `DecimalField(14,2)` / `NUMERIC`, never float; `services.bd()` validation; define and test rounding (ROUND_HALF_UP to 0.01) wherever a division/proration appears.
- **Domain services, not CRUD:** money-changing actions are functions in `services` (`post_expense`, `issue_invoice`, `receive_payment`, `pay_owner`, `pay_driver`, `reverse_entry`, `preview_settlement`, `close_settlement`, …). Don't expose editable public CRUD for ledger tables. Authorization lives in one place (`policies`), called from each endpoint; querysets are always filtered by organization and, for actors, by party scope.
- **Atomic + idempotent + locked:** multi-row postings in `transaction.atomic`; `Idempotency-Key` on posting/payments/settlement generation; `select_for_update` on rows that concurrent allocation/closing could contend on (lock in a fixed order: period → obligations by pk).
- **Immutable postings:** posted financial rows are never edited or deleted. Corrections = linked reversal + replacement, capturing who/when/why. Balances are derived or projected from postings — no authoritative editable `due` field.
- **Effective dating:** terms/rules are versioned; historical entries keep the version they were posted under.
- **Outbox in the same transaction** as the posting; send after commit.
- **Migrations:** additive first, data-migrate, then (a later milestone) remove old columns. Every data migration is reversible or documented as not. `python manage.py makemigrations --check` must be clean before you finish.
- **Tests test behaviour, not code** (spec §"ACCOUNTING AND DATA INVARIANTS"): payer vs liable party, authorized offset, partial allocation, advance, immutable reversal, historical rules, concurrent posting/close, close retry, permission boundaries, outbox retry/dedupe, statement totals vs ledger. Split `tests.py` into `rentals/tests/` (done in M0).
- **Worked-example invariants (never regress):** Sept 2026 sample — customer rent ৳100,000 / paid ৳70,000 → customer due ৳30,000; owner gross ৳60,000, authorized repair offset ৳8,000, paid ৳40,000 → owner due ৳12,000; driver salary ৳20,000, paid ৳15,000 → driver due ৳5,000; operator accrual margin ৳20,000; recorded cash movement ৳7,000. `seed_demo` must keep producing exactly this.

### M12 — Agreement dates, date-based rent and flexible payment schedule (feature 1; frontend F1). Do a short spike and a design note before coding
**Decision (user, 2026-10-09):** there are no weekly, monthly or custom-N "types" of agreement. An agreement runs from a **start date to an end date** and every calculation follows from those dates. The **payment day is a separate, flexible setting** (weekly on a weekday, monthly on a chosen day or the last day, or chosen dates). D3 (weekly settlement) is closed: nothing settles weekly; month-end closing (feature 2) stays by calendar month. This replaces the earlier `period_unit` / `period_days` / `proration` design. The Period keeps being one calendar month (`Period.month` stays unique per agreement and `Settlement` stays one per agreement and month), so the high-risk change to the monthly assumption is gone; what changes is how each month's amount is computed and how due dates are produced.
- **Dates.** `Agreement` / `AgreementVersion` carry `start_date` and `end_date`. New agreements require both (the end date can be moved by a dated revision, which is how an agreement is extended or ended early). Existing agreements keep a null `end_date` = open-ended, billed month by month as today until someone ends them. Validate end >= start, no overlap of two agreements on the same vehicle for the same dates (warn, do not block, as with driver overlap), issuing a period outside the agreement dates is refused.
- **Amounts with a basis.** Customer rent, owner rent and driver salary each have an amount and a `basis`: `per_day`, `per_month` or `fixed_total`. Existing rows are `per_month` and keep their values. Rules (ROUND_HALF_UP to 0.01, identical for all three obligations): `per_day` = days in the month that fall inside the agreement x rate; `per_month` = a full calendar month bills exactly the monthly amount, a part month bills amount x agreement days in that month / days in that month; `fixed_total` = total spread evenly over the agreement's days, rounded per day with the last day taking the remainder so the periods always add up to exactly the total. No separate proration switch: date-based calculation is always on.
- **Revisions.** A revision may take effect on any date; a month that straddles two versions is computed in dated segments with the formulas above (the design note confirms this against the M2 round-up-to-the-first rule, which stays the fallback). Old months and their history are untouched.
- **Payment schedule.** `payment_schedule` on the version, per side (customer pays us, we pay the owner, we pay the driver): `kind` = `weekly` (weekday) | `monthly` (day 1-31, or `last`) | `dates` (an explicit list). Default when unset: monthly on the last day, which keeps today's behaviour. A schedule produces derived `PaymentDue` rows (agreement, side, `due_date`, `amount`, `covers_from`, `covers_to`): each due covers the days since the previous due date (the first from `start_date`, the last up to `end_date`) using the same date maths. They are derived and regenerated for open future dues when a revision changes things, never edited by hand. Payments still allocate to the period obligations (no double counting); the dues are a view that applies paid amounts oldest-first and reports paid / partly paid / overdue.
- **Uses.** `payment_due` / `payment_overdue` reminders (M7), `customer-aging` and `Days overdue` measured from the oldest unpaid due date (end-of-month when no schedule is set, so existing numbers do not move), the colour states, the party pages, the agreement drawer.
- **API.** `issue_period(org, agreement, month)` and `POST /agreements/{id}/periods?month=` keep working; agreement create/revise accept `start_date`, `end_date`, `basis` per amount and `payment_schedule`; agreement detail returns them plus the next dues; `GET /agreements/{id}/dues`. `/snapshot` shape is unchanged (monthly periods), with the new fields additive.
- **Tests.** Agreement starting and ending mid-month; extension and early end; each basis incl. February vs a 31-day month and a `fixed_total` that must sum exactly; a revision mid-month; weekly, monthly (day and last) and chosen-date schedules; dues add up to the agreement total; oldest-first paid state; aging unchanged for a default-schedule agreement; migration of existing monthly data with identical statements; worked example unchanged (customer 30,000 / owner 12,000 / driver 5,000 / margin 20,000); a Neon run.

The agreement needs no driver party, creates no driver obligation, no salary and no driver assignment; the driver side of the statement is null and driver reports skip it; the snapshot returns the agreement with `driver: null` (frontend F21 handles it). This undoes the M3b "driver stays a required party" limitation: migration makes the driver reference nullable and every service, serializer, policy and report guards for none. Revising a no-driver agreement to add a driver later is allowed.
- **Separate driver agreement (decided by the user 2026-10-09).** When an agreement has no driver, the operator and the driver make a **simple standalone driver agreement outside the main agreement** for the salary and the staff arrangement: driver party, optional vehicle, start date, end date, salary with the M12 basis (`per_day` / `per_month` / `fixed_total`), payment day, free-text terms, optional signed document through M8. It posts into the same driver ledger (salary accrual, advances, payouts, absence deductions and fines, driver payroll, bill colours, party page) but has **no customer and no owner side** and never touches a vehicle agreement's statement or margin. Design point to settle in a short spike before coding: either a lightweight `DriverAgreement` with its own period rows feeding the existing `DRIVER_PAYABLE` / `DRIVER_SALARY_EXPENSE` accounts (preferred: the main agreement model stays strict), or an `Agreement` of kind `driver_only` with nullable customer and owner (reject if it spreads nullable checks through the services). Endpoints: `GET/POST /driver-agreements`, `GET/PATCH /driver-agreements/{id}` (dated revisions like the main agreement), listed on the driver's party page (M10). Tests: salary accrues and is paid without any vehicle agreement; the worked example's figures do not move; a driver with both a standalone agreement and a driver on a vehicle agreement keeps two separate balances that the party page sums with a visible split; absence deductions and fines work on either. Frontend F21 gets the screen.
- **Extra charge kinds on the M4 charges engine (no new engine).** `overtime` (customer, increases the amount due; quantity x rate, e.g. hours, with an optional `overtime_rate` / `overtime_unit` on the agreement version), `absence_deduction` (driver, decreases the salary due; quantity in days x the driver's daily rate from M12, suggested but editable), `fine` (customer or driver, increases the customer's due or decreases the driver's salary; reason mandatory, proof optional through M8). All need a reason, an idempotency key and approval above the usual threshold; all are audited; all appear on statements, the ledger, income and the party pages. If no rate is set on the agreement the user types the amount.
- **Protected ID data.** `Party` gains optional `nid_number` and `driving_licence_number`, and documents of category `identity` (M8). New policy action `party.read_ids` (admin only). Other roles see masked values (last four) or nothing; the values are excluded from list endpoints, `/snapshot`, reports, exports and notification bodies; every read is logged `sensitive.read`.
- **Tests.** No-driver agreement end to end (issue, expense, payment, settlement, reports) with the worked example's customer and owner figures unchanged; adding a driver by revision; each charge kind changes the right side and reconciles; ID data hidden from a non-admin and absent from exports; migrations on existing data.

### M15 — Vehicle papers (optional) and expiry reminders (feature 8 and vehicle records). After M7
- `VehiclePaper` (vehicle, `type`: registration | fitness | tax_token | insurance | route_permit | custom, `custom_name`, `number` optional, `issue_date` optional, `expiry_date`, optional attached document through M8). **Nothing is required**: a vehicle is created and used without papers, and no agreement, expense, payment or closing step is ever blocked by a missing or expired paper.
- Reminder settings in `OrgSettings`: lead times (default 30, 15 and 7 days before expiry) and an on/off switch per paper type (default on). Reminders go to the admin only, through the M7 notices (SMS, email, in-app), event `vehicle_paper_expiring`, once per paper per lead time; editing an expiry date resets that paper's reminders. Only papers with an expiry date are reminded. An expired paper shows as expired on the vehicle page and the overview.
- Endpoints: `GET/POST /vehicles/{id}/papers`, `PATCH/DELETE /vehicle-papers/{id}` (delete allowed: a paper is a reminder, not accounting data), `GET /vehicle-papers?expiring_within=N`. Audited. Branch scope applies. Paper data may appear in exports.
- Tests: a vehicle with no papers works end to end; one reminder per lead time; editing resets; admin-only recipient; nothing in billing or closing reads a paper; branch scope.
